# Data access and handling

This document sets out how programme data may enter, be held in, and leave the TB decision support system. It applies
before any real (non-synthetic) record is loaded. It is a technical policy for the project team and must sit under the
data-sharing agreement with NHM Assam and the approvals of the relevant ethics committee; where they differ, those
documents prevail.

## 1. What data the system uses

| Source | Status | Where |
|---|---|---|
| NTEP District RoP 2024-26 (planning targets, capacity) | Public, real | `data/public/`, see `SOURCES.md` |
| Patient, laboratory, referral and facility records | **Synthetic** in this repository | generated by `tbds/synth` |
| Nikshay programme extract | Real, restricted | never in this repository; see section 3 |

The pipeline needs only the fields it models: demographics (age, sex), clinical and programme variables (dates,
bacteriological status, drug resistance, HIV, diabetes, BMI, adherence, Nikshay Poshan enrolment), facility and district,
and outcomes. Request nothing beyond this list.

## 2. Roles and least privilege

Access is role-based and enforced by the API (`tbds/api/security.py`):

| Role | Sees | Identifiers |
|---|---|---|
| State admin | State-wide aggregates; patient lists in pilot districts; audit log | Never |
| Data manager | Duplicate queue and data quality, state-wide | One patient at a time, with a reason |
| District TB officer | Own district | One patient at a time, with a reason |
| Facility user / field worker | Own facility | One patient at a time, with a reason |

* Analytic tables hold a **pseudonymous key** only: `HMAC-SHA256(pseudonym_salt, nikshay_id)`, truncated.
* Names, guardian names, phone numbers and villages live in a separate `identities` table. The API returns them only
  through `/patients/{key}/identity`, for one patient, after the user gives a reason of at least 8 characters.
* Duplicate review shows masked names (`V**** Y****`).
* Every view, export, decision, identity reveal, sign-in and failed sign-in is written to `audit_log`.

## 3. Receiving an extract

1. The extract is prepared by NHM Assam staff inside the government environment, limited to the fields in section 1.
2. **The pseudonym salt is generated and held by NHM Assam**, not by the analytics team. It is passed to the pipeline
   only through the environment variable `TBDS__SECURITY__PSEUDONYM_SALT` at run time and is never written to disk,
   logs or this repository.
3. Files are transferred only by the channel named in the data-sharing agreement (e.g. a government SFTP host), never by
   email or consumer file-sharing services.
4. Files are placed on the processing server outside the repository, e.g. `/srv/tbds/extract/`, in the format the
   loader expects: `patients`, `facilities`, `lab_results` and `referrals`, each as `.parquet` or `.csv`.
5. Set:

   ```
   TBDS__DATA__SOURCE=extract
   TBDS__DATA__EXTRACT_PATH=/srv/tbds/extract
   ```

   then run `python -m tbds.cli run-all`. The loader pseudonymises keys before any analytic table is written.
6. `.gitignore` excludes `data/extract/`, `data/private/`, `*.parquet` and `*.xlsx`. Do not override it.

## 4. Storage and security

* PostgreSQL runs on government-approved infrastructure, with disk encryption and backups restricted to the project's
  database administrators.
* The API runs with `TBDS__APP__ENV=production`, which refuses to start while any development default is set
  (see `docs/DEPLOYMENT.md`).
* All traffic uses HTTPS. The dashboard's offline cache stores only the page itself, never API responses.
* Revealed identifiers are held in the browser's memory for the session only and are cleared on sign-out or reload.

## 5. Outputs and sharing

* Reports and exports leave the system as aggregates or pseudonymous lists. CSV exports carry the decision-support notice
  and are audit-logged.
* Suppress counts below 5 in anything published outside the programme. The system does not do this automatically;
  whoever prepares a publication is responsible for it.
* Model cards, validation figures and this repository may be shared; patient-level data may not.

## 6. Retention and deletion

* Extract files are deleted from the processing server once loaded and verified, and in any case within 30 days.
* Database contents are kept for the pilot period plus the retention period in the data-sharing agreement, then deleted
  (`python -m tbds.cli init-db --drop` followed by deletion of backups).
* `audit_log` is retained for the full period and exported to the programme before deletion.

## 7. Before live use

* Re-validate both risk models on the pilot districts' own retrospective data, and record the results in the model cards.
* Review subgroup performance (sex, age, tribal community, tea-garden workers, hill districts, sector) for fairness.
* Confirm the role list and named users with the State TB Cell; remove all demo accounts.
* Run a privacy impact assessment covering the identity-reveal workflow.
